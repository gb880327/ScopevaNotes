## Context

v1 已完成（70/70，主规格尚未归档，`openspec/specs/` 无基线）。数据层是单连接 `Mutex<Connection>` + `spawn_blocking`（v1 D1），写路径 `note_repo::create` 是「一笔记一事务 + `search_index::reindex_note`」，`notes_fts` 由写路径投影维护而非触发器。库是单个 `.db` 文件，备份靠 `VACUUM INTO`。

约束：
- 迁移的终点通常是用户删掉 Obsidian vault，所以「没搬进来的东西」等于永久丢失，必须在报告里说清。
- 预览是裸 markdown-it + 协议白名单，不认 Obsidian 扩展语法（`[[…]]`、`==…==`、`%%…%%`、`> [!note]`）。
- 前端只有 `services/commands.ts` 触碰 IPC；没有 `fs` 插件，读文件的代码只能在 Rust 侧。
- 单连接意味着批量写入期间会与自动保存抢同一把锁。

## Goals / Non-Goals

**Goals:**
- 一次导入结束后，用户能凭报告判断「能不能删原目录」，不需要逐个文件抽查。
- 重跑与中断重试是安全的：不会产生重复笔记，也不会留下半条。
- 导入的笔记立刻可用：能搜、能编辑、能打标签、顺序符合直觉。
- 保真：正文除 frontmatter 外逐字不变，因此后续渲染层改进不需要重新导入。

**Non-Goals:**
- 不做目录监听、双向同步、增量更新（本 change 的「更新已存在」就是「跳过」）。
- 不迁移附件/图片，不实现图片渲染或 asset 协议。
- 不解析 `[[双链]]` 为内部链接，不做跳转、反链、图谱。
- 不渲染数学公式、Mermaid、Dataview 等插件语法。
- 不做导出回 Markdown。

## Decisions

**D1 导入只搬字节，只剥 frontmatter —— 不解释 Obsidian 语法。** 导入阶段的唯一正文改动是移除开头那段 YAML（它是元数据，不是正文）；`[[链接]]`、`==高亮==`、`%%注释%%`、`> [!note]`、`^块引用`、`![](img/a.png)` 全部原样保留。

理由：这些语法的「正确渲染」是渲染层的责任，而渲染层可以独立演进。若导入时就把 `==x==` 改写成 `<mark>x</mark>`、把 `%%…%%` 删掉，那么将来渲染层做好了也拿不回原文 —— 数据损失不可逆，而渲染改进是可逆的本地产出。代价是迁移后第一眼看到的仍是裸 `[[…]]` 与可见的 `%%注释%%`，由报告里的「本版不解析 Obsidian 扩展语法」承接说明。

这一点修正了规划阶段的一个口头建议（当时打算在导入时剥 callout 标记与注释），原因是那条路把渲染问题和数据问题绑在一起。

**D2 附件不迁移，但「未迁移」必须被计数。** 图片等本地文件不复制、不改写、不存储。报告给出「N 条笔记引用了本地文件，本版未迁移」。导出方案（把字节搬进 `<库目录>/assets/` 并改写为相对链接）已评估：技术上可行，但会把备份语义从「一个 `VACUUM INTO` 文件」变成「db + 目录」，牵动已完成的 5.x 备份与 `docs/RELEASE.md`。既然 v1 定义为纯笔记工具，这条留到附件功能单独立项。备选「data URI 内联进正文」被否：正文变不可读、导出即失真。

**D3 `source_path` 是三重用途的一列，`content_hash` 是预留列。** `source_path`（导入文件的绝对路径）同时提供：重试安全（存在即跳过）、出处审计（报告能说「这条来自 `Projects/x.md`」）、将来附件解析的基准目录。它是可空列，手工新建的笔记为 NULL，因此不影响既有 DTO 契约；索引用部分唯一索引（`WHERE source_path IS NOT NULL`）兜住并发/重复写入。

`content_hash` 本 change **不驱动任何行为**：只记录，供将来做「同一路径内容变了」的同步判断。承认它是死数据，接受的理由是——一次性迁移的用户在半年后重跑一次的概率不低，那时若没有哈希就只能整目录重来。

**D4 分批提交，每批 200 条，取消即停在批边界。** 单连接下逐条提交 5,000 次会有 5,000 次 fsync；单个大事务则让自动保存被锁住整分钟。200 条/批在实测里应是几十毫秒量级，批次之间可以发布进度、读取取消标志。取消后已提交的批次保留并计入报告（与「导入不是事务性的」这一点在规格里写明）。

**D5 导入与自动保存的冲突当作可见错误处理，不当作静默重试。** 导入持锁期间编辑器的保存会失败，走既有的 `AppError::Busy` → 前端可见提示 → 笔记保持 dirty 待重试。不做「导入期间暂停自动保存」的隐式降级：用户不知道自己刚才的输入没落盘，比看到错误更糟。

**D6 时间戳取文件系统元数据。** `mtime` → `updated_at`，`birthtime` → `created_at`（APFS 有，缺失回退 `mtime`，再缺失回退 `now`）。未来时间（时钟错乱、从别的机器拷来的文件）钳到 `now`，避免一条笔记永远置顶。备选「全部用 now」会让 300 条导入笔记挤出列表顶部并埋掉既有笔记。

**D7 解码：UTF-8 优先，GB18030 兜底，各自记录。** 先 `std::str::from_utf8`；失败用 `encoding_rs::GB18030` 解码。GB18030 几乎不会失败（大多数字节序列都合法），所以判定顺序必须是「UTF-8 不合法才走 GB」，否则中文 UTF-8 文件会被错误地按 GB 解码成乱码。新增 Rust 依赖 `encoding_rs`（无 unsafe、无 C 依赖）。

**D8 frontmatter 用手写子集解析，不引入 YAML crate。** 只认三个键：`title`、`tags`、`created`。支持 `tags: [a, b]`、`tags: a, b`、block list（`- a` 缩进行）。理由：完整 YAML 解析只是个位数百分比的收益，却要引入一个维护状态参差的 crate 并处理锚点/多行字符串/引用等无人使用的语法。代价明确记入限制：非这三个键的 frontmatter 一律丢弃，`created` 解析失败则回退文件时间。

**D9 导入复用既有写路径，不新建第二套。** `note_repo` 增加一个批量插入入口，内部仍走 `replace_tags` + `search_index`，与 `create` 同源。这样 FTS 投影、`explode_cjk`、CJK 前缀匹配全部自动一致，不需要为导入单独维护索引逻辑，也不再跑一次全量 `reindex_all`。批量插入用的是索引模块**新增**的 append-only 入口（见 D14），而不是 `reindex_note` —— 两者共用同一份 `insert_row`，不是两套逻辑。

**D10 撤销靠批次标签，不加批次表。** 整批写入时创建/复用一个 `import-YYYY-MM-DD` 标签并挂到本批全部笔记；「删除本批」= 按该标签软删除（进回收站，可恢复）。好处：零 schema 成本、用户也能自己按标签筛选；代价：同一天两次导入共用一个标签，撤销会一起撤销 —— 在报告文案里写明日期粒度。

**D11 预览与执行分两条命令。** `import_scan(path)` 只返回统计（计数 + 跳过原因分布 + 未迁移引用数），`import_notes(path, options)` 才写库。预览不需要写权限，也不会因为用户中途放弃而留下痕迹；两者共用同一套发现/解析代码，避免「预览说 300、实际导 280」的漂移。

**D12 进度与取消走事件 + 共享状态。** 进度用 `ui://import-progress`（`AppHandle::emit`），取消用 `state.rs` 里的 `AtomicBool`，命令执行期间在批间检查。复用既有 `quitting`/`quit_pending` 的原子标志风格，不引入 channel。

**D13 报告是一个 DTO，不是若干条日志。** 一个 `ImportReport { imported, skippedExisting, failed[], hiddenSkipped, decodedAsGb18030, localFileReferences, cancelled, elapsedMs }`，前端只做渲染；错误文案由 Rust 侧给出（含路径），避免前端拼接路径时丢失上下文。逐文件失败清单只在 `failed` 非空时展示。

**D14 导入写入用 append-only 的索引入口，不用 `reindex_note`。** `notes_fts.note_id` 是 `UNINDEXED`，所以每一条 `DELETE FROM notes_fts WHERE note_id = ?` 都是一次全表扫描；`reindex_note` = 先删后插，逐条调用在导入时变成 O(n²)。导入的笔记一定是新 id、不可能已有索引行，于是给 `search_index` 加 `index_new_note()`（与 `reindex_note` 共用 `insert_row`），导入路径直接追加。

实测（release，20 个目录 / 每篇 ~600 字中文，`cargo test --release --test import_bench -- --ignored`）：

| 规模 | 改前 | 改后 | 单批最长间隔（自动保存最坏等待上界） |
| --- | --- | --- | --- |
| 1,000 条 | 0.49 s | 0.49 s | 101 ms |
| 5,000 条 | **9.52 s** | **2.12 s** | 131 ms（改前 756 ms） |

批量 500 条时 5,000 条降到 1.55 s，但单批最长间隔升到 172 ms。默认仍是 200（D4）：总时长差 0.6 s 不值得换更长的锁窗口。

## Risks / Trade-offs

- **保真 vs 第一眼观感**：迁移后 `[[笔记]]`、`%%注释%%` 仍然裸着。选择保真是因为渲染改进可以事后做，正文改写不能事后撤销。缓解：报告首屏写明「本版不解析 Obsidian 扩展语法，原文已完整保留」。
- **附件留在原地**：用户删掉 vault 后，所有图片链接永久失效。缓解只在报告与文档（`RELEASE.md`）里，这是本 change 最大的、明确接受的残差风险。
- **GB18030 误判**：任意字节序列大概率是合法 GB18030，判错方向（把 UTF-8 当 GB）会造成乱码。用「UTF-8 优先」的判定顺序把这种可能压到只剩「既非 UTF-8 又是坏 GB」，此时记为失败而非写入乱码。
- **同日批次共用一个撤销标签**：撤销粒度是日期，不是「这一次」。若用户一天导两次并想只撤第二次，做不到；记录为已知限制。
- **导入期间的锁竞争**：5,000 条实测单批最长间隔 131 ms，远低于 5 s 的 `busy_timeout`；但 10k+ 且正文更长的库会更慢。缓解是分批 + 进度 + 可见错误；根治需要写入队列，属于数据层重构，不在本 change。
- **`index_new_note` 的正确性依赖调用方**：它不做删除，只允许用于「该 id 尚不存在于索引」的新笔记。今天只有导入路径调用；若将来有别的入口复用，必须先确认这一点。
- **frontmatter 子集解析**：`tags:` 写成多行 YAML 字符串（`tags: |`）或带锚点时不解析，标签会缺失。记为限制，不猜测。
- **大库体积**：`explode_cjk` 让 FTS 索引随正文线性膨胀（10k 条实测约 14.6 MB→库 14.6 MB 级别）。导入 5k 条中文笔记后库会明显变大，接受，因为这是 v1 既定的搜索设计。
