## Context

See `proposal.md` — Why。现状约束：

- 数据层已经分开了：`tags(id, name COLLATE NOCASE UNIQUE, color, created_at)` + `note_tags(note_id, tag_id)`（两侧 `ON DELETE CASCADE`），正文里不存标签。所以"实体与关系分离"不是待做的事，而是待**让界面遵守**的事。
- 后端已有 `tag_repo::{create, rename, delete}`；`delete` 在同一事务里删 `tags` 行（`note_tags` 级联）后对每条受影响笔记调 `search_index::reindex_note`。
- `note_repo::update` 已接受 `tagIds: Option<Vec<String>>`，同事务 `replace_tags` + `reindex_note`。
- 侧栏结构：`Sidebar.vue` → `NoteList` / `TrashList` / `TagList`（`TagList` 只占高度 38%，一行是"色点 + 名称 + 计数"，点击整行 = 过滤）。`TagEditor.vue` 是一个无样式约束的裸输入框（现在只用于新建）。
- 产品契约：单主窗口、无第三栏、无多窗口。

## Goals / Non-Goals

**Goals:**

- 标签的四个动作（新增 / 重命名 / 改色 / 删除）都在侧栏就地完成，一步可达，且都能看到后果（计数、受影响笔记数）。
- 笔记上的标签从"只读文本"变成可编辑 chip，走既有写路径而不是第二套写入逻辑。
- 失败可见：冲突、空名、孤儿标签都必须在界面上呈现，不静默。

**Non-Goals:**

- 不做独立的标签管理页 / 第三栏 / 独立窗口（见 D1）。
- 不做标签层级 / 嵌套树（`a/b` 仍只是一等名称字符串）。
- 不做标签合并（重命名到已存在名称即报冲突）。
- 不做多选笔记批量打标签。
- 不新增 `tags` 表列或迁移；不把标签写回正文。

## Decisions

**D1 管理入口 = 现有侧栏标签列表本身，行内就地编辑。**
理由：`TagList` 已经是"全部标签 + 颜色 + 可见笔记数"，再开一个管理界面等于把同一份数据在两处渲染、两处维护。侧栏就在笔记列表旁边，重命名一眼能看到笔记上的 chip 跟着变，符合"就地改、立刻看到后果"。备选与取舍：
- 设置模态里的「标签」section（本 change 初稿的方案）→ 否：低频操作却要开模态、切 section，改完看不到笔记列表的反应。
- 独立窗口 / 第三栏 → 违反产品契约。

**D2 实体操作放侧栏，关系操作放笔记头部；不为"分开管理"做任何数据改造。**
理由：用户问的"标签和内容是否分开管理、再建关系"——数据层已经是这样（两张表 + 多对多关系），不存在需要重构的耦合。真正的耦合只在界面上：现在标签看起来像"内容的一部分"，因为唯一的标签 UI 出现在笔记头部只读文本里。按实体/关系切分之后：侧栏 = `tags` 表的增删改（改名、改色、删除实体），笔记头部 = `note_tags` 关系的增删（挂上、摘掉）。这也顺带解释了为什么删除标签不该删笔记——删的是实体，关系靠级联消失。

**D3 行内手势：点名称区 = 过滤；hover 出两个图标按钮（重命名 / 删除）；重命名把整行换成输入框。**
理由：点击行过滤是既有手感和既有测试契约，不能为了编辑牺牲它；把编辑放在行尾图标上，误触概率最低。重命名复用 `TagEditor` 的输入框（回车提交、Esc 取消、失焦取消），不引入弹窗。备选（双击改名 / 右键菜单）→ 否：双击与单击过滤会互相干扰，右键在 macOS 上不可发现。

**D4 删除确认在行内二次点击，文案带受影响笔记数。**
理由：与导入报告里的「删除本批」一致（同为 destructive + 内联确认），可测且不弹原生对话框；行内确认还能顺手显示"将影响 N 条笔记"，这个 N 直接来自 `list_with_counts` 的 `noteCount`，不需要新查询。确认按钮不是默认焦点，Esc 取消。

**D5 改色 = 行内色点展开固定调色板（8 个令牌色），不引入颜色选择器依赖。**
理由：`tags.color` 是自由字符串，但界面只需要"能区分标签"；8 个取自设计令牌的色值足够，且能保证浅深两套主题下都有对比度（调色板色值来自 `--accent-*` 系列）。

**D6 笔记标签编辑复用 `update_note` 的 `tagIds`。**
理由：`update` 已保证"改标签 → 重建索引 → 冲突检测"在同一事务里；另开 `add_note_tag` / `remove_note_tag` 会造成第二套写路径与第二套索引维护点（导入 D9 的同类错误）。代价是每次 chip 操作发一次完整 `update_note`，与"改标题"的代价相同。

**D7 "输入新名称即建即挂" = 先 `create_tag` 再 `update_note`，不合并成一条命令。**
理由：合并需要在 `update_note` 里 upsert，会改动已冻结的 DTO 与并发语义。两步的失败模式（标签建好但没挂上）必须**可见**：提示"标签已创建，但挂到笔记失败"，且该标签会出现在侧栏——用户可再挂一次，而不是留下一个看不见的孤儿。

**D8 计数不做乐观本地加减，操作成功后重取 `list_tags`。**
理由：计数由单查询给出（`标签列表带计数` 要求不得按标签逐个查询），乐观加减一旦偏差就会长期存在；标签操作低频，重取更省心。

## Risks / Trade-offs

- **侧栏只有 ~200px**：hover 出现两个图标会挤掉计数。→ 两个按钮绝对定位在行右端，hover 时隐藏计数（`opacity` 切换，不改变行高）；重命名时整行变输入框，计数与色点隐藏。
- **误触删除**：行内确认让"删除"变成两次点击，且第一次不聚焦确认按钮；Esc 取消。→ 仍需组件测试断言"取消时不发命令"。
- **删除被大量笔记使用的标签是 O(N²)**：`delete` 对每条受影响笔记调 `reindex_note`，而 `notes_fts.note_id` 是 UNINDEXED，「先删后插」每次全表扫描（见 `mem:search`、导入 D14）。1,000 条共用同一标签时会退化成秒级。→ 确认文案给出受影响条数；任务里加基准；若实测 > 1 s，再考虑"清空 + 全量重建"。
- **两步创建留下孤儿标签**：见 D7，靠可见提示 + 侧栏兜底。
- **chip 行与标题争宽度**：标签多时头部会换行挤压标题。→ 标签区独立一行、超出横向滚动，与既有 `.meta` 行一致。
